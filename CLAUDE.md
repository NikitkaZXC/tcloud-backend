# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project

tcloud: a FastAPI service that stores media (photo, video, audio, GIF) and other files of any type (non-media is served only as a sandboxed attachment: `attachment` + `nosniff` + CSP `sandbox`, docs/security.md) in private Telegram channels ("storages") through a Telegram **user** account (Telethon). Every file has a UUID and a path `tcloud/{storage uuid}/{folders}/{name}`; PostgreSQL keeps the index. Python 3.14, managed with `uv`. Structure and rules mirror `~/Desktop/nextgate/nextgate-backend`. Detailed docs (Russian) are in `docs/` (index `docs/README.md`).

## Architecture

Layers: `api → application → infrastructure`; `utilities` are shared. `src/application` never imports `src/api`; `src/infrastructure` imports neither.

- `src/api/`: routers (`routes/`), HTTP schemas (JSON bodies subclass `schemas/base.RequestBody`, `extra="forbid"` → `422`; query models stay lenient), `middleware/` (body size cap `APP_MAX_BODY_SIZE` → `413 body_too_large` except the streaming upload/photo routes in `body_limit.STREAMING`, security headers, `Origin` check against CSRF; CORS for `APP_ALLOWED_ORIGINS` with credentials in `main.py`), `exception/` (error code → HTTP status table, handlers, body `{"error": {"code", "message", ...}}`), `dependencies/get_actor` (access cookie or `X-API-Key` → `Actor`) and `get_root`. All routes are under `/api`, aggregated in `endpoints.py`; `/api/telegram` is root-only.
- `src/application/services/`: one class per domain (`AccountService`, `AuthService`, `HealthService`, `StorageService`, `FolderService`, `FileService`, `TaskService`, `UploadService`, `UserAuthService`, `UserService`, `GrantService`, `ApiKeyService`, `SettingsService`) plus `UploadPipeline` (stages run by Celery workers). Services take an `AsyncSession` and `AppRuntime`, build repositories in `__init__`, **own the commit**. Routes get services only via `src/application/factory/get_service_*`.
- `src/application/schemas/`: service DTOs; `src/application/exception/`: domain errors; `bootstrap/`: `startup`.
- `src/infrastructure/`: `database/` (models end with `DB`, mixins give UUIDv7 `id`/`created_at`/`updated_at`, repositories only `flush()`, migrations), `integrations/` (`telegram`, `antivirus`, `web`), `media/` (type sniffing, Pillow/ffprobe, thumbnails), `background/` (Celery app with priority queues `uploads.download`/`uploads.prepare`/`uploads.telegram`/`archives.build`, `enqueue`, `queue_sizes`, `DiskBudget`, `AppRuntime`, `WorkerRuntime`, `Heartbeat`), `cache/` (`TaskStore` in Redis with Lua `CLAIM`/`REQUEUE`/`CANCEL`), `enums/`, `logger/`, `limits.py` (all Telegram limits).
- `src/utilities/`: `errors.TCloudError` (base error with `code`), `parsers/` (paths, Range), `formatters/` (constrained request types).
- Errors: every error subclasses `TCloudError` with a stable `code`; only the API layer maps codes to HTTP statuses. Telethon exceptions never leave `integrations/telegram` (`translate_errors`).
- Uploads: API writes the body to the shared `tmp` volume, task state lives in Redis (no tasks table), Celery on RabbitMQ runs `src/application/tasks`. Workers use `--pool threads`; `WorkerRuntime` runs one event loop per worker process with its own Telethon session (`TELEGRAM_UPLOAD_SESSION`). **Run one `worker-telegram` replica** (shared FloodWait pause). Reads from Telegram stay in the API on a separate client and session (`runtime.download`, `TELEGRAM_DOWNLOAD_SESSION`). Queue messages carry only `task_id` + `generation`; a worker must `claim` before work (stale generation, cancelled or duplicate messages are skipped). `sent`/`committed` in the task make Telegram sends idempotent on redelivery. `TaskSweeper` in the API fails tasks lost by the broker.

## Gotchas

- Telethon picks photo vs document by file extension: temp files keep the extension of the target name.
- Compressed photos: Telethon's `file.size` is the heaviest `PhotoSize`, but `iter_download(media)` fetches `sizes[-1]`, which may be lighter. Size, download, `Range` and archives all go through `photo_size`/`download_location` in `integrations/telegram/client.py` (heaviest `PhotoSize`/`PhotoSizeProgressive`).
- API DB pool has no `pool_pre_ping`; `ReconnectingSession` (`database/session.py`) retries the first statement of a transaction once when the connection was invalidated (Postgres restart), `pool_recycle` = `POSTGRES_POOL_RECYCLE`.
- Reads after ORM `UPDATE` with `onupdate=func.now()` need `populate_existing=True`, otherwise async lazy load raises `MissingGreenlet`.
- `media/analyze.py` is not called `probe.py` on purpose: the package exports a `probe` function.
- ClamAV image must be `*-debian` (alpine tags are amd64 only); stream limits are raised and alerts made strict in `docker/clamd.conf` (`test_clamd_config_is_strict` guards it). `Heuristics.Encrypted|Limits.Exceeded|OLE2.ContainsMacros` mean `unscannable`, every other hit is `infected`. libclamav caps `MaxFileSize` at 2147483645 bytes; `CLAMAV_MAX_FILE_SIZE` mirrors it and bigger files skip ClamAV with warning `too_big_to_scan` regardless of `allow_unscannable` (`test_scan_limit_mirrors_clamd_config`).
- Tests: `tests/conftest.py` sets `TEST_ENV` (with `ENV_FILE=""`) before importing `src`; API tests patch `main.create_telegram`/`main.create_login`/`main.create_scanner` with `tests/fakes.py` (the `upload_session` fixture creates the upload session file uploads require) and run real Celery workers in threads on `memory://` (session-scoped), swapping `src.application.tasks.upload.runtime` per test.
- Never run several embedded Celery workers on RabbitMQ in one process (shared kombu hub corrupts AMQP frames): API tests use `memory://`; ordering and crash tests spawn real `celery worker` processes (`tests/integration/test_workers_e2e.py`).
- Only the API Telegram client has `receive_updates=True` (`TelegramClient.watch`: manual deletions in Telegram drop DB rows via `events.MessageDeleted`; an `events.Raw` handler for `UpdateChannel`, title/photo service messages and our own `UpdateUser` only deletes the Redis caches `channel:*`, `channel_photo:*`, `account:*`, never calls Telegram; docs/flows/storages.md «События Telegram»); register handlers before `catch_up()`. Workers create clients with `receive_updates=False`.
- Users: roles `root` (single, synced from `ROOT_LOGIN`/`ROOT_PASSWORD` on every API start), `admin`, `user`; no self sign-up, login + password only (no email). JWT RS256 in HttpOnly cookies (`access`/`refresh`, keys in `certs/`), refresh rotation with reuse detection, revoked access `jti` in Redis. Per-user API keys in `X-API-Key`; any password change (admin `PATCH`, own `/auth/password`) and role change delete them. Rights are read from the DB on every request, never from the token. Every service method that touches storages/folders/files/tasks takes an `Actor`; checks live in `services/access.py` (grant `recursive` = folder and below, otherwise only files directly in it; `can_read/can_upload/can_delete`). Tasks carry `user_id`; users see only their own (docs/flows/users.md).
- Telegram login is API-only and root-only (`/api/telegram/{api|upload|download}/qr|code|sign-in|password|logout`); the app starts without sessions and Telegram calls answer `503 telegram_unauthorized`. Login state lives in API process memory (one uvicorn process). `TelegramLogin` writes `login-*.session` and atomically replaces the session file on success. Never add a session that accepts foreign QR tokens. Default paths are local `data/...`; compose sets `/data/...`.
- Folder archives (`POST /api/folders/archive`; arbitrary selections of one storage via `POST /api/folders/archive/selection`, entries relative to the common parent folder, deduped, ≤ `UPLOAD_ARCHIVE_MAX_ITEMS`; both go through `FolderService._queue_archive`, which caps files at `UPLOAD_ARCHIVE_MAX_FILES` and bytes at `UPLOAD_ARCHIVE_MAX_SIZE_MB` and allows one unfinished archive task per user (`409 archive_in_progress`, checked under `job:disk`); zip/7z/tar.gz/tar.bz2/tar.xz at compression level 6, `archive.LEVEL`) are background tasks (`params.source = archive`, stage `archiving`) on queue `archives.build`, consumed by the single `worker-telegram` (upload session reads the files); the ready file stays in `UPLOAD_TMP_DIR` for `UPLOAD_ARCHIVE_TTL` (Redis zset `archives`, removed by `TaskSweeper.clean_tmp`) and is downloaded via `GET /api/tasks/{id}/archive` by the task owner only. `UPLOAD_MAX_ACTIVE_TASKS`/`UPLOAD_MAX_FILES_ON_DISK` = 0 means unlimited (default); only `UPLOAD_MIN_FREE_DISK_MB` guards the disk.
- Encryption is on by default: `encrypt` is tri-state (`None` → on for `send_as=file`, off for `send_as=media`; explicit `true` with media → `422 encrypt_requires_file`; explicit `false` → plaintext), resolved in `UploadService._new_task`. Tests about plaintext pass `encrypt="false"`. Details: `infrastructure/security/encryption.py`, AES-256-GCM in 64 KiB blocks, per-file DEK wrapped by `APP_ENCRYPTION_KEY`; header in the TG file and `files.encryption_header`; `files.size` is the plaintext size, the TG size is `cipher_size(size)` (`services/file.stored_size`); download/archives decrypt via `services/file.file_body`. Losing the key loses the files.
- Big files (docs/flows/uploads.md «Большие файлы частями»): a file whose stored size (cipher for encrypted) exceeds `limits.file_limit(premium)` is split at send time by `security.part_spans` (encrypted: at GCM block boundaries of the one whole-file stream, so each part decrypts alone with the DB header) and sent sequentially as documents (`{uuid}.part{N}.bin` / `{name}.part{N}`; `send_as=media` → warning `too_big_sent_as_file`). Rows in `file_parts` (offset/size in stored bytes) exist only for multi-part files; `files.tg_message_id` is part 0. Every reader goes through `services/file.open_pieces` + `file_body(read, pieces, …)`; delete paths use `layout()` / `get_messages_below` (includes parts); a Telegram delete of any part drops the file and deletes the other parts. `sent.parts`/`sent.spans` make resume after a crash continue from the next part. `sending` {file_id, chat_id, after, spans} is stored before the first part: on redelivery `find_sent` reads channel history after `after` for our caption `#tc{file_id}`, adopts the next expected part (same name and size) into `sent` and deletes other unrecorded ones; `fail`/skip delete them too (fakes need `last_message_id`/`find_sent`). Tests force tiny parts by patching `pipeline.file_limit`. Root's `uploads.max_file_size` (0 = unlimited) is the only size limit (`413 too_large`).
- Resumable uploads (docs/flows/uploads.md «частями»): `POST /api/uploads/sessions?size=` runs `_new_task` checks, locks the path, takes the disk slot, creates an empty temp file and stores `{task, offset, expires_at}` in Redis `upload_session:{id}` (+ zset `upload_sessions`; `session_id` = future task id, owner-only, others 404); `PUT ?offset=` appends one chunk ≤ `UPLOAD_CHUNK_SIZE` under `TaskStore.holding("upload:{id}")` (`409 upload_session_busy`), `offset_mismatch` returns the current `offset`, any error/disconnect truncates back (`temp.append_body`); the last chunk goes through `UploadService._queue_device` like `POST /api/uploads`. `TaskSweeper.clean_tmp` keeps live session files and drops expired sessions (`expires_at = min(last chunk + UPLOAD_SESSION_IDLE_TTL, started_at + UPLOAD_SESSION_TTL)`). Per-user quotas (root exempt, checked under `job:disk`): `UPLOAD_USER_MAX_SESSIONS` (`429 too_many_upload_sessions`) and `UPLOAD_USER_DISK_QUOTA_MB` over live sessions + per task the larger of its `disk:usage` entry (`TaskStore.use_disk`: `{task: "user:bytes"}` full footprint, written under `job:disk` before the body is read, kept until `release`; finished archives as `archive:{id}` until their TTL; quota only, never in the global disk check) and its `disk:reserved` remainder (`TaskStore.user_disk`, `507 temp_quota_exceeded`); archives are checked too (`upload.check_quota`, the `disk:usage` entry is written only after the ledger hold succeeds). Managers (mirror of `get_manageable`) list (`GET /api/uploads/sessions?user_id=`) and `DELETE` others' sessions; blocking/deleting a user runs `temp.cancel_user_sessions` and `temp.cancel_user_tasks` (every unfinished task from `user_tasks:{user}` through `temp.cancel_task`, the same path as `POST /api/tasks/{id}/cancel`, final webhook for tasks with `callback_url`). Every disk check goes through async `DiskBudget.check`/`hold`/`reserve` (API and workers; workers get `disk.store` in `WorkerRuntime`) and subtracts bytes not yet written to disk by any process: live sessions (`TaskStore.session_bytes(exclude)`: `size − offset`, `+ size` if encrypted; a chunk excludes its own session; a session has no ledger entry) plus the Redis ledger `disk:reserved` {owner: bytes} + `disk:reserved:exp` {owner: expires_at} (`reserved_bytes`, Lua `RESERVED` drops expired). Owner = task id (previews: file id); an entry is `expected − written`. POST body, URL upload with a known size (optional `size` of `from-url`/batch items, kept in `params.size` and on retry; in the worker it caps the download: other `Content-Length` or shorter body → `size_mismatch`, longer → `too_large`) and queued archives reserve at creation under the short Redis lock `job:disk` (`TaskStore.disk_lock`, 5 s TTL, bounded wait, then proceeds unlocked with a warning); workers reserve per stage (download, ciphertext, archive build, preview) and `release(keep)` parks the bytes the next stage still needs (`UPLOAD_LOCK_TTL`). A live `Reservation` syncs its remainder and re-reads others once per `SYNC_INTERVAL` (1 s) with a 30 s expiry; `TaskStore.deactivate` (so every `release`) drops the entry; a dead holder drops out by expiry; redelivery re-reserves by the same owner (own entry excluded from its check).
- User settings (`GET/PATCH/DELETE /api/account/settings`, docs/flows/settings.md) live in `users.settings` JSONB (only keys the user set; defaults from `SettingsServiceRead`) and ride in `Actor.settings` (no extra query). Stored JSON is read tolerantly (`SettingsServiceRead.from_stored` in `UserAuthService.actor`): unknown groups/keys are dropped and invalid values fall back to defaults with a warning per key, so removing or renaming a key or `Literal` value needs no migration; the cleaned value is written on the next save. `PATCH` stays strict (`extra="forbid"`) and merges into the stored column re-read under `SELECT … FOR UPDATE` (`UserRepository.get_for_update`), not into the request's `Actor.settings`, so concurrent PATCHes never drop keys. Omitted upload/archive params fall back to them (`UploadServiceCreate.with_defaults`, start of `FolderService.create_*archive`); explicit params win; `encrypt` unset + effective `media` stays off; empty `callback_url` disables the settings webhook. Webhooks are validated by `web.check_webhook`. Only root's `telegram.chat_folder` matters (one Telegram account): `StorageService.sync_folder` keeps all storage channels in the Telegram chat folder "TCloud" after storage create/delete, `TELEGRAM_CHATS` connect and a root change of the setting; folder errors are only logged.
- `FileService._media` reads `(media, size)` through `runtime.media` (`MediaCache`, in-process LRU, 2000 entries, 90 s; misses of one chat within 20 ms are coalesced into one `messages_media` = `GetMessages(ids=[…])`, fakes need `messages_media`); `forget_deleted`, `forget_edited` (`events.MessageEdited`) and file/folder delete call `runtime.media.forget`; `TelegramFileReferenceError` → forget, re-read, retry once per part (`FileService.body`, thumbnails). The DB row and rights are still checked every request.
- Thumbnails (`GET /api/files/{id}/thumb`) are Telegram's own sizes (largest ≤ `THUMB_SIDE`, stripped ones skipped) read by `runtime.download` and cached in Redis `thumb:{file_id}:{message_id}` for `REDIS_CACHE_TTL` under a total cap `REDIS_THUMB_CACHE_MB` (Lua `KEEP_THUMB` evicts oldest; accounting in `thumbs`/`thumbs:size`/`thumbs:bytes`). Encrypted photo/GIF/video get our own preview (`media.preview`, ≤ 320 px, ≤ ~20 KB JPEG, made in `UploadPipeline._encrypt` from the plaintext, sealed with the file DEK via `security.seal`) in deferred `files.thumbnail`, decrypted by `/thumb`; never sent to Telegram; failure → `NULL` + warning; root's `POST /api/files/previews/backfill` queues `previews.backfill` (`PreviewBackfill`, on `archives.build`, upload session, one job at a time via Redis `job:previews`) that fills missing ones. Root's `uploads.previews` (default `true`, ignored for others) switches previews off for everyone: `_preview` skips the `previewing` step, backfill answers `409 previews_disabled` and a running job stops before its next batch; `GET /api/account` exposes it as `previews_enabled` (`storage.root_settings`). Root's `DELETE /api/files/previews` nulls every `thumbnail` in 1000-row transactions (`ix_files_preview`) → `{cleared, bytes}`. `replace` keeps the file id, so the cache key is `ETag` = message id, not the URL.
- Access in SQL: `access.read_scopes(actor)` → `(storage_id, folder, recursive)` list (`None` for admins) → `repositories/like.readable(...)`; used by search, folder sizes and storage stats so unreadable files never leak into counts. Search (`GET /api/files/search`, `/search/mimes`) relies on `pg_trgm` (migration `0006`) and DB locale `en_US.utf8` for Unicode `lower()`.
- Search name sort uses ICU collations `tcloud_ru`/`tcloud_en` (migration `0010`, `lang` param); their `COLLATE` indexes are invisible to SQLAlchemy reflection, so `migrations/env.py` skips `COLLATED_INDEXES` in autogenerate.
- Folder listing (`GET /api/folders`) is paginated: `items` (folders and files, `type` discriminator), keyset `next_cursor` (base64url JSON with the sort, group, keys, id; another sort → `422 invalid_cursor`), sort params default to the user's `interface` settings, `limit` 20 (≤ 200; the frontend sends `interface.page_size`). Totals (`size`, `total_files`, `total_folders`, `direct_files`) only on the first page (null with a cursor); folder sizes only for folders on the page (one `GROUP BY`) unless the full aggregate already ran; no Telegram calls. Visible subfolders go into the SQL as `VALUES`, files use the `ix_files_list_*` indexes (migration `0013`, collated ones listed in `COLLATED_INDEXES`); the `type` key expression in `repositories/file.file_type` must stay textually equal to the index (constants inlined, not bound).
- Storage channel info (title, about, has_photo) is cached in Redis `channel:{chat_id}` for `REDIS_CACHE_TTL` (180 s) (`StorageService.channel_infos`, used by storage list/get and search); our own edits/photo/delete drop the key (`forget_channel`, also drops the avatar bytes `channel_photo:{chat_id}`, base64, served by `GET /storages/{id}/photo` with a content-hash `ETag`/`304`); a Telegram error serves what is cached and marks the rest `available: false`.
- Telegram account info (`premium` → Telegram message limit = part size of big files, `channels_used`) is cached in Redis `account:premium`/`account:channels` for `REDIS_CACHE_TTL` (`AccountService`); storage create/delete, `TELEGRAM_CHATS` connect and API session login call `store.forget_account()`.
- Read/write LEDs: every operation runs inside `TaskStore.active(storage, kind)`: its member in zset `activity:{storage}:{read|write}` scores now+5 s, refreshed every 1 s, and now+1 s (`ACTIVITY_TAIL`) on exit, including errors, cancellation and client disconnect (download stream via `services/file.tracked`, Telegram delete of file/folder, `UploadPipeline.run` for `uploads.telegram`/`archives.build`); `GET /api/storages/activity` counts members with a future score (pipelined `ZCOUNT`).
- Telegram reconnect: Telethon gives up after 5 auto-reconnects; every `translate_errors` call first runs `TelegramClient.ensure_connected` (reconnect a started-but-dropped client under a lock, exponential pause 1…60 s answering `telegram_unavailable` meanwhile) in API and workers; the API also pokes both clients every 15 s (`AuthService.run_keepalive`). Fakes need `ensure_connected` and `ping`. Health Telegram checks are a real `updates.GetState` (`TelegramClient.ping`, 5 s timeout, cached 5 s); `telegram_upload` comes from the worker heartbeat JSON `{at, telegram}` (`WorkerRuntime.telegram_state`), falling back to the session file while the worker has no client yet.
- Tasks may outlive `UPLOAD_LOCK_TTL`: the worker heartbeat and every `TaskSweeper.sweep` call `TaskStore.renew` (Lua `RENEW_TASK`: own path lock, `active`/`disk` scores, parked `disk:reserved` and `disk:usage` expiry); startup `prepare` keeps old tmp files of active tasks, live sessions and archives (`temp.used_files`). `_beat`/`_watch` log Redis errors and keep looping.
- RabbitMQ `consumer_timeout` must stay raised (compose sets 24 h), otherwise long Telegram uploads lose their channel at 30 min.
- Broker drops (docs/background-tasks.md «Обрыв RabbitMQ»): publishes use `confirm_publish` (without it `kill -9` of RabbitMQ lost queued messages); a message redelivered while the first run still beats (`beat_at` fresher than 3 heartbeats) gets `CLAIM_BUSY` and waits, then runs only if the stage is still its own (`claim(..., waited=True)`), otherwise two copies uploaded the same file; a worker handoff retries a down broker for `BROKER_WAIT` (10 min) before `queue_unavailable`.
- Celery pidbox queues are `control_queue_exclusive=False` + `control_queue_durable=True` (10 s `x-expires`): an exclusive pidbox stays locked by the dead connection after a network drop and the reconnecting worker died with `ResourceLocked`; RabbitMQ 4 rejects transient non-exclusive queues, hence durable (`tests/unit/test_celery_config.py`).

## Rules

- Plan first, then implement by the plan. Important decisions go to the owner as multiple-choice questions.
- README stays short: overview, diagrams, main endpoints table, launch, links; details go into `docs/`.
- Tests for every new feature (the more the better). Keep `docs/`, `README.md` and this file current in the same change; schema changes → `docs/database.md`.
- When code changes a flow shown in `docs/`, update the doc and its diagram in the same commit (Mermaid blocks; check they render with `mmdc` installed outside the repo). New Redis keys → `docs/redis.md`.
- Every new query with a filter or sort gets an index. All our ids are UUID. Never edit existing migrations.
- Respect Telegram limits (`src/infrastructure/limits.py`, `docs/integrations.md`).
- Endpoint rate limits are set in the routes (`rate_limit_by_ip` / `rate_limit_by_user` / `RateLimiter.hit`, or router-level in `endpoints.py`); values live in `RATE_LIMIT_*` (`src/config/models/rate_limit.py`, docs/security.md).
- No code comments or docstrings (one-line docstrings on exception classes only); explanations go to `docs/`.
- Log with loguru; never log secrets.
- Commits: one-line English messages (`feat:`, `fix:`, `refactor:`), one per logical change. **Never push.**
